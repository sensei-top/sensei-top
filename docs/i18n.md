# Translation

The app is read in English or Brazilian Portuguese. Every sentence a user
sees is looked up by a key, in three places that translate separately:
the dashboard (`web/`), the API's prose (`src/sensei_top/`), and the
desktop shell (`desktop/`). English is the source in all three, and a
missing translation is always English, never an error or an empty space.

This page is how a string gets keyed, what is never translated, and how
to add a language. Magic's own Portuguese terms are in the glossary at the
end.

## The language, from setting to sentence

The dashboard holds the setting; the server stores none. The choice is made on
the desktop app's first welcome step (English or Português (Brasil),
pre-selected from the language the installer ran in on Windows, the computer's
elsewhere) and on Settings, which adds "System". A shell keeps it in
`shell.json` as `language` (`i18n.ts`'s `setLanguage` writes it through
`app.set`, and at the next start the shell's value wins); a plain browser
keeps it in its own storage. "System" is the first English or Portuguese tag
among the viewer's languages, Portuguese of any region giving `pt-BR`, and
English when there is none (`systemLanguage`); it follows the browser's
`languagechange`. `web/src/i18n.ts` resolves the choice to a language, and
`web/src/api.ts` sends it as `Accept-Language` on every request.
`api/app.py`'s middleware enters `i18n.use_language()` for that request, so
every `_()` the route reaches answers in that language. A change of language
re-renders the dashboard and resets React Query's cache (every query but the
live one), so prose the API wrote in the old language is fetched again.

The API negotiates two languages: any Portuguese tag (`pt-BR`, `pt`,
`pt-PT`) is Brazilian Portuguese, anything else is English
(`i18n.language_for`).

## Keying a string in the dashboard

i18next and react-i18next. Catalogues are JSON files,
`web/src/locales/<language>/<namespace>.json`, one namespace per area of
the app (`shell`, `settings`, `matches`, `decks`, …). `i18n.ts` picks them
up with `import.meta.glob`, so a new namespace file needs no registration.

- **A key is written whole, its namespace first:**
  `t('settings.backup.title')` is `backup.title` in
  `locales/<language>/settings.json`. Keys are semantic (what the text is
  for), never the English text itself.
- **A component takes `t` from `useTranslation()`**, which re-renders it
  when the language changes. A function in `lib/*.ts` that builds a
  sentence takes `t: TFunction` as an argument, so its test can pass
  `translator('en')` and read the real catalogue. `currentT()` is for the
  rare caller outside both (`lib/time.ts`'s `ago`), and is called where the
  text is built, never at module load.
- **Counts use i18next's plurals**: `matches_one`, `matches_other`, called
  as `t('…matches', { count })`. The forms follow `Intl.PluralRules`,
  not English: Portuguese's `one` covers zero as well as one
  (`new Intl.PluralRules('pt-BR').select(0)` is `one`), so its `_one`
  form is written knowing it will also be read with 0. Portuguese's
  `many` covers whole millions (`select(1000000)` is `many`) and numbers
  written with an exponent, neither of which the dashboard shows as a
  count.
- **Markup inside a sentence goes through `<Trans>`** with named
  components, so a translation can move the bold word.
- **A number, a percentage, a date or a list goes through
  `lib/format.ts`** (`formatNumber`, `formatPercent`, `formatDate`,
  `formatRelative`, `formatList`, `formatFixed`, `formatDollars`), never
  `toFixed`, `toLocaleString` or a hand-written `%`. It follows the
  language the text resolved to, so a sentence never mixes English words
  with Portuguese separators.

`web/scripts/i18nCheck.test.ts` (part of `pnpm test`) walks `src/` and
fails on a JSX text node, a literal in a text attribute, or a `t()` key
the English catalogue lacks. It cannot see a sentence built in a `.ts`
file, an object literal's label or a key built at run time; those are
found by reading the file. Its `NEVER_KEYED` list is the design reference
pages (below).

## Keying a string in the API

Stdlib `gettext`, wrapped in `src/sensei_top/i18n.py`; its module
docstring lists the traps in full.

- **The English text is the msgid**: `_("No games yet")`,
  `ngettext("{n} game", "{n} games", n).format(n=i18n.integer(n))`.
- **Named placeholders only**, filled with `.format(...)` after the
  lookup, never an f-string or `%s`: a translation may reorder them.
- **No `_()` at import time.** A module-level display constant is marked
  `N_("…")` and translated where it is used, `_(CONSTANT)`.
- **Numbers in a sentence** go through `i18n.decimal`, `i18n.percent`,
  `i18n.integer`, and a list of names through `i18n.join`, which match the
  dashboard's `format.ts`.
- After adding or changing a string, run
  `uv run python scripts/i18n_extract.py`: it rewrites
  `src/sensei_top/locale/sensei_top.pot`, and `tests/test_i18n.py` fails
  while the template is stale. The extractor refuses a call it cannot
  read (a variable, an f-string, a positional placeholder, a call at
  import time) rather than skipping it.

Catalogues are `src/sensei_top/locale/<lang>/LC_MESSAGES/sensei_top.po`,
read once at startup with `polib` and compiled in memory. No `.mo` file is
generated or tracked. A `.po` that does not parse, or one entry whose
placeholders differ from its msgid's, is served as English with a
warning.

## Keying a string in the shell

`desktop/` cannot import from `web/`, so the shell has a small catalogue
of its own: `desktop/src/locales/<language>.json`, flat, one key per
string, read by `desktop/src/i18n.ts`.

- **`t('tray.menu.quit')`** from `i18n.ts`; the key's type is the English
  catalogue's keys, so a misspelt one fails `typecheck`. Placeholders are
  `{name}`, filled from the call's second argument.
- **A missing translation is English**, then the key itself; never an
  error.
- **The language** is `shell.json`'s `language`, set at launch and again
  by Settings through `app.set` (`SettingsService.setApp` calls
  `setLanguage`); "system" is the first English or Portuguese tag among
  `app.getPreferredSystemLanguages()`, the same rule as the dashboard's.
  The tray rebuilds its menu and tooltip on a change (`onLanguageChange`);
  a dialog reads its words when it opens.
- **The installer** (`desktop/build/installer.nsh`) speaks NSIS's own
  languages: `electron-builder.yml` lists `en_US` and `pt_BR`, the
  installer asks which on start, and every custom page's text is a
  `LangString` in a `customHeader` macro, one line per language. The
  language it ran in goes into `first-run.json` beside the autostart
  choice (`"language": "pt-BR"`), and the shell's first launch copies it
  into `shell.json` unless a language was already chosen, so the welcome
  step opens pre-selected to it. It only seeds: the welcome step and
  Settings still decide.

## Every prompt is English

A prompt is model input, and it carries the app's own sentences: a
match-report finding's `title` and `detail` reach both the dashboard and
the match-report and coach prompts. **Every prompt builder runs under
`i18n.english()`** (a context manager, used as a decorator), so whatever
it formats comes out in English, whatever language the request asked for.

`english()` cannot reach back in time: an object built before the builder
ran, in the request's language, carries its translated text in. A prompt
builds its own evidence inside its own scope; it is never handed a report
a page already rendered. `tests/test_i18n.py` builds every prompt under a
Portuguese request and compares it with English.

## What is never translated

- **Card, deck and archetype names.** Card names stay as Arena's log and
  Scryfall give them, in English. A deck's name stays as the user wrote
  it. An archetype's name stays as the corpus or the rule engine
  (`archetypes/`) names it, including one written as a literal in code.
  Only the words around a name are keyed, with the name as a value.
- **Prompts** (above), and the **Markdown exports** of the deck guide and
  the RCQ guide, which are prompt input and carry English model prose.
- **Stored prose**: a written narrative, brief, coach report or RCQ guide
  stays in the language it was written in.
- **The CLI and log lines.** Console output, warnings and
  `logs/sensei-top.log` stay English.
- **`docs/` and `docs/user/`.**
- **The design reference pages** (`/design`, `/design/surfaces`,
  `views/DesignView.tsx`, `views/SurfacesView.tsx`, `lib/sampleShell.ts`):
  a developer's reference, not a page users reach.
- **Test files.**

## Adding a language

1. **Dashboard:** a folder `web/src/locales/<language>/` with one JSON
   file per English namespace, the same keys, and the language added to
   `LANGUAGES` and `systemLanguage` in `web/src/i18n.ts`. Its plural forms
   are i18next's for that language (`_one`, `_few`, `_many`, `_other` as
   `Intl.PluralRules` names them).
2. **API:** `src/sensei_top/locale/<lang>/LC_MESSAGES/sensei_top.po` from
   the `.pot`, with the language's `Plural-Forms` header (gettext's own
   formula for it), the language added to `TRANSLATED` in `i18n.py` and to
   `language_for`, and its separators to `_SEPARATORS` if they differ from
   English's.
3. **Shell:** `desktop/src/locales/<language>.json` with the same keys,
   the language added to `LANGUAGES` and `systemLanguage` in
   `desktop/src/i18n.ts`, a `LangString` line per text in
   `desktop/build/installer.nsh`, the language in
   `desktop/electron-builder.yml`'s `installerLanguages`, and its LCID,
   spelt out as the top of `installer.nsh` does for Brazilian Portuguese,
   in the macro that writes `first-run.json`.
4. A section of its own in the glossary below.

## Glossary

Magic has its own vocabulary in every language, and Wizards already chose
it: on the printed cards, in the rulebook, and in Arena's own client. The
glossary records that choice once, so the three catalogues (dashboard,
API, shell) use the same word for the same thing, and a translator picks
a row rather than a synonym. **Nothing here is coined.** Every row names
its source; the few terms no Wizards text settles (the strategy jargon
players write but Wizards never prints) are marked *usage* and were
approved by the user, not sourced. Two rows (*sideboard*, *no play / no
draw*) are the user's choice of the players' word over Arena's own; the
row says so and names Arena's.

What a row never covers: a card, deck or archetype name, which stays as
it is (see "What is never translated"). The glossary gives the words
*around* a name.

### Português (Brasil)

**Sources**, cited by letter in the tables:

- **A** — Arena's client strings: `Raw_ClientLocalization_*.mtga` under
  the installed client's `MTGA_Data/Downloads/Raw/`, table `Loc`,
  columns `enUS` and `ptBR`. The words the user sees in Arena itself.
  Read with a read-only, immutable SQLite connection; nothing Arena owns
  is ever written.
- **C** — Arena's card database beside it, `Raw_CardDatabase_*.mtga`
  (`Enums` for types and colours, `Localizations_ptBR` for rules text).
  Scryfall's `lang:pt` printings say the same for every zone and type
  checked.
- **K** — Wizards' Portuguese keyword glossary,
  <https://magic.wizards.com/pt-br/keyword-glossary>.
- **R** — Wizards' Portuguese basic rulebook (M14, 2013),
  <https://media.wizards.com/images/magic/resources/rules/PT_MTGM14_Rulebook_Web.pdf>;
  its own glossary defines *partida* and *jogo*.
- **F** — Wizards' Portuguese formats page,
  <https://magic.wizards.com/pt-BR/formats>, and the Timeless
  announcement,
  <https://magic.wizards.com/pt-BR/news/mtg-arena/introducing-timeless-a-new-mtg-arena-format>.
- **U** — *usage*: what Brazilian players and strategy sites write where
  no Wizards text names the thing. Approved by the user in phase 4a
  (2026-10-09), not sourced.

Where Arena (A) and the website (F) differ, Arena wins: the app sits
beside the client, and the user reads both.

**Five rules that span the tables**

1. **A card is a *card*, never a *carta*.** Every Wizards source says
   *card* (A "Reserva: 15 cards ou menos", C "Compre um card", R, K).
   Masculine: *o card, os cards*.
2. **A match is a *partida*; a game is a *jogo*.** The rulebook's
   glossary (R): "*Partida*: uma série de jogos contra o mesmo oponente.
   A maioria das partidas consiste numa 'melhor de três', portanto, o
   primeiro jogador a vencer dois jogos vence a partida." Arena's own
   strings blur the two ("Vença uma partida pareada" for a game); the
   app does not, because it counts both. *Game 1* is *jogo 1*.
3. **The sideboard stays *sideboard*** (m., *o sideboard*), the user's
   call (U, 2026-10-09): it is what Brazilian players and strategy sites
   write ("Deck Tech e Guia de Sideboard"). Arena's client says
   *Reserva* ("Reserva: 15 cards ou menos", "Voltar à Reserva", "Decks
   de Brawl não têm reserva"), so a reader of both meets two words for
   one thing; where the app first teaches the term it may say "o
   sideboard (a Reserva, no Arena)" once. Sideboarding, the act, is
   *as trocas de sideboard*; a sideboard plan is *plano de sideboard*.
4. **A *mulligan* is a mulligan**, masculine, done with *fazer*: "fazer
   um mulligan", "mulligan para seis" (A, R). The alternative is *manter*
   (A: "Manter", "manter a mão"), and the hand is the *mão inicial* (A,
   R). Never *mulligar*.
5. ***Draw* is two words.** Drawing a card is *comprar* (A, C, R); the
   result that is neither a win nor a loss is *empate* (A "Draw →
   Empate", R "o jogo é um empate"). The English catalogue uses both
   senses; the Portuguese row depends on which.

**Gender and number, for the catalogues.** *o card, o deck, o sideboard, o
grimório, o cemitério, o exílio, a mão, o campo de batalha, a pilha, a
mesa, o mulligan, a partida, o jogo, o turno, a mágica, o feitiço, a
criatura, o terreno, a ficha, o marcador, a classificação, a temporada, o
arquétipo, o matchup, o metajogo, o leak.* Portuguese's `one` plural form
also covers zero ("0 partida", as the grammar norm has it; gettext's
formula for Portuguese, `plural=(n > 1)`, agrees), so the `_one` text is
written knowing 0 will read it too. Where that reads oddly, a count of
none gets its own key ("Nenhuma partida").
